# Office 文档写作策略（按体裁）

本文件是 Word 内容引擎所有阶段的共同写作基准：先读通用红线，再按体裁执行。

## 通用红线（所有体裁）

1. 禁止机械化分点：不要为了“显得有结构”给每个段落加小标题，也不要通篇“第一、第二、第三”“首先、其次、再次、最后”。分点只在确实存在并列要素（步骤、指标、选项）时使用，且同层级不超过 5 项。
2. 禁止空洞总结：不得写“本节介绍了……”“具有重要意义”“起到了积极作用”“为后续工作奠定基础”这类没有信息增量的句子。每个段落至少包含一项可检验内容：事实、数字、机制、步骤、判断依据或明确结论。
3. 禁止套话与连接词堆砌：一段内最多一个过渡词；全文避免“众所周知 / 不难发现 / 显而易见 / 值得注意的是 / 综上所述 / 总而言之 / 希望对你有帮助 / 让我们一起”。直接用事实与因果衔接。
4. 禁止虚构：不得编造数据、百分比、倍数、文献、法规条款、人名、机构名或案例。只有输入素材（facts）明确给出的数字和出处才能写；素材缺失时用定性表述（“明显提升”“尚需进一步验证”）或标注“待补充/需核实”，不得伪造来源。
5. 禁止重复表达：同一句、同一短语不要在不同段落反复出现；合并同义段落，章节之间要有信息递进而非复制。
6. 语气统一：全篇人称、时态、术语一致；中文正式书面语，避免口语、感叹号与营销腔。
7. 事实优先：先给结论再给依据；没有依据的判断写成假设（“我们推测……”）而不是事实（“事实证明……”）。

## 学术论文（academic）

- 结构：摘要（目的/方法/结果/结论）、引言（问题、现状、缺口）、研究方法（数据来源、样本、实验或模型设计）、结果与分析、讨论、结论与展望、参考文献。
- 必须出现方法 / 结果 / 结论类章节标题。
- 数据必须带出处（数据来源、样本量、统计口径），不得编造文献；引用只在 facts 中给出时使用。
- 使用客观第三人称，避免“我们认为”“大家都知道”。

## 商业计划书 / 项目方案（business-plan）

- 结构：执行摘要、市场与用户、产品/方案、商业模式、实施路径（里程碑）、团队、预算与财务测算、风险与应对。
- 必须覆盖目标 / 实施 / 风险 / 预算四类内容。
- 预算与市场数据只能来自 facts；没有数据时写“需财务测算”并给出测算口径，不得拍脑袋造数字。

## 工作报告 / 总结（work-report）

- 结构：本周期目标与完成情况、关键数据、问题与原因、改进措施、下周期计划与责任人。
- 数据必须可比（同比/环比口径写清楚），没有口径就说明“口径待确认”。
- 计划要可执行：动作、责任人、时间点，避免“继续努力”“加强协同”这类口号。

## 调研报告（research-report）

- 结构：调研背景与目的、对象与方法（样本、问卷/访谈方式）、调研发现、数据分析、结论与建议。
- 方法与样本必须交代清楚；百分比要说明样本基数与来源。
- 发现要分条但按“结论 + 证据”组织，不写流水账。

## 会议纪要（meeting-minutes）

- 必须包含：时间、地点、参会人员、议题、结论（或决议）、待办事项（责任人 + 截止时间）。
- 只记录会上实际发生的内容，不补充会上未讨论的推断。
- 结论与待办要明确，避免“进一步沟通”“持续跟进”等模糊表述（除非会上原话如此并注明负责人）。

## 技术设计文档（tech-design）

- 结构：背景与目标、总体架构（模块划分与依赖）、接口设计（API/协议/数据结构）、数据与存储、关键流程与异常处理、部署与运维、风险与取舍。
- 必须覆盖架构 / 接口 / 部署三类内容。
- 接口写清输入、输出、错误码；架构写清模块边界与调用方向；不得虚构不存在的组件或性能数字。

## 简历 / 个人介绍（resume）

- 不使用封面页，不写目录；篇幅控制在 1-2 页。
- 以要点化经历为主：岗位/项目 + 动作 + 可量化结果；不要大段自述，单段控制在 150 字以内。
- 只写 facts 中提供的信息，不编造学历、公司、时间与业绩数字。

## 正式通知 / 公文（notice）

- 必须包含：事项（通知什么）、时间（生效/执行/截止时间）、要求（谁做什么、如何反馈）。
- 语言简洁、庄重，不抒情、不铺垫；标题可直接用“关于……的通知”。
- 不编造文号、落款机构；缺失信息标注“待补充”。
