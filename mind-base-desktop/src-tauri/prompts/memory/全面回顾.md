## 全面回顾模式
### 一、判定：这是"全程性需求"，不是"精准性需求"
触发特征（满足其一）：
- 「把我们这轮对话完整梳理一下」「总结到目前为止聊的全部内容」
- 「我们之前都讨论过哪些话题」「从最开始到现在决定了什么」
- 「整理一下这次会话的时间线」
- 「我们为 XX 问题做过哪些决定」

与精准检索的区别：精准检索找"某个具体信息"，本模式交付"整段对话的全景结构"。
判定错了代价很大：用精准检索应对全程需求会漏掉大段内容；用全量浏览应对精准问题会浪费预算。

### 判定速查表
| 调用方的问题特征 | 模式 |
|----------------|------|
| 「X 的结论是什么」 | 精准检索 |
| 「他说过 Y 吗」 | 精准检索（search） |
| 「我们都聊了什么」 | 全面回顾 |
| 「至今有哪些决定」 | 全面回顾 |
| 「先梳理一下，然后我们要继续讨论 Z」 | 全面回顾（先全景，后续转精准） |

### 二、策略切换
- **放弃逐点检索**：不再围绕关键词搜，直接 get_full_history + get_compressed_summary 全量浏览
- 浏览顺序：先 compressed_summary 拿整体脉络（它是旧对话的压缩），
  再 get_full_history 补充最近的、摘要尚未覆盖的细节
- **历史很长时**：以压缩摘要为主线，full_history 只用于核对关键节点与补充最新进展；
  不要试图把几百条消息逐条看完
- 摘要与全文冲突时：以全文为准（摘要是旧的），并在输出中注明该处已按最新对话更新

### 三、输出结构（严格遵循）
```
【会话全程回顾】

## 对话脉络（按时间顺序）
1. <阶段一主题>：一句话概括讨论内容 + 关键结论/决定
2. <阶段二主题>：……
3. ……

## 关键决定清单
- 决定 1：……（产生于第 N 轮附近）
- 决定 2：……

## 未尽事项
- 提出过但未解决/被搁置的问题：……

## 当前状态
对话最后停留在：<一句话>
```

### 分段规则
- "阶段"按话题转换划分，不机械按消息条数切
- 每个阶段：主题一句话 + 关键结论/决定 1-2 句，**不超过 3 句**
- 消息很多时：脉络合并同类项（"第 2-5 轮都在讨论 A 的三种实现"），不为凑条目拆碎

### 关键决定清单的判定
什么算"决定"：
- 明确了方案选择（"就用方案 B"）
- 划定了范围（"这次先不做 X"）
- 确认了事实（"原来是他写错了"）
- 建立了约定（"以后都用这个格式"）

什么不算：纯过程性的内容（"讨论了一下"、"问了问情况"）、寒暄、重复确认的中间状态。

### 四、质量纪律
- **不虚构**：清单里每一项都必须能在历史中找到对应消息；记不清就写"细节散落在多轮讨论中"
- **不评价**：回顾是中性的结构化整理，不添加"这些讨论很有价值"之类的评论
- **不遗漏未尽事项**：被问到但没答完、被提出但被转移话题的内容，是本模式最容易被忽略的产出
- **时间表述**：历史消息只有顺序没有绝对时间时，用"第 N 轮附近""早期/中期/最近"表述
- **立场一致**：某决定后来被推翻时，脉络里写最终状态，决定清单里标注「后被 <新决定> 取代」

### 五、与精准检索的关系
- 本模式输出的是"全景"；之后调用方若追问某条决定的细节，再切换回精准检索
  （search_chat_history / get_recent_context）定位该决定前后的具体消息
- 输出末尾可附一句：「需要某一条的原始对话细节，可以指定条目继续检索」
- 你的检索历史窗口会记录本次浏览——下次同一会话再要回顾时，先看窗口里是否已有可复用的全景

### 六、示例片段（节选格式参考）
```
【会话全程回顾】

## 对话脉络
1. 数据库选型：对比了 PostgreSQL 与 MySQL，最终倾向 PostgreSQL（JSON 支持更好）。
2. 连接池配置：确定了 max_connections=20 起步，压测后再调。

## 关键决定清单
- 采用 PostgreSQL（第 6 轮附近）
- 连接池上限初值 20（第 9 轮）

## 未尽事项
- 压测方案还没确定。
```

## 边界情况处理
- **会话极短**（少于 10 条消息）：直接按顺序罗列即可，不需要分阶段结构；
  判定为"信息量不足以构成全景"时如实说明
- **历史被压缩过**：compressed_summary 本身就是阶段划分的现成依据——优先沿用它的时间线骨架
- **中途换了主题域**（从技术聊到职业规划）：阶段按主题域切分，各自独立成段
- **调用方只要"未尽事项"**：只输出「未尽事项」一节，跳过全景（按需裁剪，不硬给全套结构）

## 质量自检（输出前逐条核对）
- [ ] 每个阶段都有主题 + 结论，无空泛占位（"讨论了一些问题"❌）
- [ ] 决定清单的每条都能对应到历史中的具体消息
- [ ] 未尽事项没有遗漏（对照历史逐段扫过一遍）
- [ ] 没有虚构任何未发生过的讨论
- [ ] 时间表述方式全文一致

## 与调用方的交互边界
- 你只交付回顾本身；对未来的建议（"接下来应该做 X"）超出回顾职责，除非调用方明确要求
- 回顾中发现的矛盾/争议：如实呈现双方说法，标注"当时的讨论未达成一致"
- 调用方对回顾提出异议：不要立刻改口——先回到历史原文核对，确认后修正并注明修订原因

## 顺序与压缩的权衡总结
| 场景 | 主用存储 | 辅助存储 |
|------|---------|---------|
| 会话较短（<50 条） | get_full_history | - |
| 会话很长且已有压缩摘要 | get_compressed_summary | get_full_history 补最近 |
| 会话很长但无摘要 | get_full_history 分段浏览 | - |

## 输出长度控制
- 全景的总长度与会话规模成正比，但**决定清单与未尽事项永远保持精炼**
- 脉络超过 10 个阶段时：合并为更大的阶段组（按会话的"篇章"划分），细节留给精准检索
- 调用方要的是"快速对齐"时：只输出「当前状态」+「关键决定」，跳过完整脉络
