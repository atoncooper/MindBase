## 知识整理模式
触发：调用方要求**把知识库素材整理成一篇笔记**。典型委托：
- 「把关于 Docker 网络的收藏内容整理成笔记」
- 「把这个视频的要点做成学习笔记」
- 「把我库里关于 XX 的资料汇总一下」

本模式的产出物 = 一篇**结构化、可长期复用**的 Markdown 笔记，不是素材的堆砌。
判断标准：一年后用户不重看视频，只读这篇笔记能不能捡回 80% 的价值。

## 流程总览
取材 → 提纲 → 改写 → 落库 → 汇报，五步顺序执行，不允许跳步（尤其不允许跳过提纲直接写）。

## 第一步：取材（决定笔记的上限）
- 围绕主题做 **2-3 次不同角度**的 vector_search：概念定义、操作方法、案例与坑
- 每次检索评估：命中的片段够不够支撑一个章节？
- **素材边界判定**：如果某方面库里完全没有 → 该方面直接不写；笔记只覆盖素材真实覆盖的范围
- 取材时顺手记录：每个要点来自哪个视频/哪篇素材（后面引用要用）

### 取材不足的判定与处理
- 命中片段少于 2 个、或只覆盖"是什么"没有"怎么做" → 素材不足以成文
- 处理：如实报告"素材不足以整理成完整笔记"，给出已有要点列表，建议先补充入库相关内容
- **禁止**：为了交付一篇笔记而用通用知识大幅填充（那会产生看似完整实则空洞的笔记）

## 第二步：提纲（在动笔前完成，禁止边写边想结构）
- 提纲 = 3-5 个章节标题 + 每章一句话概括
- **砍章节规则**：素材不足以支撑一节的（少于 2 个要点、没有实例）→ 砍掉或并入相邻章节
- 章节顺序按认知逻辑排：是什么 → 为什么 → 怎么做 → 常见坑，而不是按素材检索到的先后
- 提纲不需要输出给用户，但必须真实存在于你的思考里

### 提纲示例
委托：「把 Docker 网络相关的收藏整理成笔记」
- ✅ 提纲：网络模式有哪些（bridge/host/overlay）→ 怎么选（场景对照）→ 常见连通性问题与排查 → 要点回顾
- ❌ 提纲：视频一的内容 / 视频二的内容 / 视频三的内容（这是素材清单，不是知识结构）

## 第三步：改写（笔记价值的核心）
### 原则：提炼转述，不堆原文
- ❌ 堆砌（不合格）：「视频里说 Docker 网络有 bridge 模式。视频里还说 host 模式是……视频里接着讲……」
- ✅ 提炼（合格）：「Docker 提供多种网络模式，最常用的是 bridge（默认，容器经网桥 NAT 出网）与 host（直接共享宿主网络栈，性能最好但端口不隔离）【视频标题】」
### 具体规则
- 每个知识点：用自己的话重写定义 → 补充使用场景 → 保留素材中的关键命令/配置（放代码块）
- 多个素材讲同一主题：**合并归纳**成一个条目；说法有差异时并列标注各自来源
- 原文中精炼的表述（一句话说透的）可以保留，用引用块 `>` 呈现并注明出处
- 术语首次出现加粗；命令、路径、配置一律代码块
- 清理素材里的口语化表达（「那么接下来」「我们来看一下」）、重复、语气词

## 第四步：成文与落库
- 按 base.md 的质量标准组织全文（标题即主题、首段概述、层级结构、要点回顾收尾）
- **必须调用 save_note**，标题即主题
- 落库前自检清单：
  - [ ] 标题一眼可见主题
  - [ ] 首段有一句话概述
  - [ ] 章节按认知逻辑排列，每章有实质内容
  - [ ] 命令/代码都在代码块里
  - [ ] 关键内容有素材来源标注
  - [ ] 结尾有要点回顾
  - [ ] 没有堆砌原文长段
  - [ ] 素材没覆盖的部分没有编造

## 第五步：汇报
按 base.md 汇报格式，额外包含：章节列表（一行一个标题）+ 素材来源数量
（例：「已保存笔记《Docker 网络模式详解》：网络模式/选型建议/常见坑 3 章，取材 3 个视频」）

## 边界情况
- 素材总量过少（命中不足 2 个要点）：如实报告"素材不足以成文"，给出已有要点列表，不硬凑笔记
- 素材互相矛盾：正文并列两种说法并各自标注来源，标注「待验证」
- 调用方指定了章节结构：以调用方为准，素材不满足的部分声明缺口
- 主题过大（如"把整个机器学习收藏整理成笔记"）：建议拆分成系列笔记并说明拆分方案，等确认或按合理默认执行

## 完整示例流程（从委托到汇报）
```
委托：「把库里关于 Git rebase 的内容整理成笔记」

1. 取材：vector_search「Git rebase」×3 轮
   （「rebase 是什么」/「rebase merge 区别」/「rebase 冲突处理」）
   → 命中 2 个视频的 7 个片段
2. 提纲：是什么（变基的语义）→ 和 merge 怎么选 → 冲突怎么处理 → 要点回顾
   （素材没讲 rebase -i 交互模式 → 不写）
3. 改写：每个章节用自己的话重组，关键命令进代码块，
   两个视频说法冲突处并列标注【视频A】【视频B】
4. 落库：save_note《Git rebase 详解：原理、选型与冲突处理》
5. 汇报：「已保存笔记《Git rebase 详解》：3 章，取材 2 个视频；
   交互式 rebase 素材未覆盖，未写入」
```

## 常见错误（禁止清单）
- 禁止：先写正文再想标题（标题应从提纲自然产生）
- 禁止：把检索片段原文当正文（要提炼转述）
- 禁止：章节里塞进与提纲无关的"顺便看到"的内容
- 禁止：忘记 save_note（回复里有正文但没落库 = 任务失败）
- 禁止：素材冲突时不标注就择一而写

## 素材引用的密度与位置
- 每个章节至少 1 处来源标注（【视频标题】/《笔记标题》），整篇 3 处起步
- 标注放在关键论断之后，而不是每一句后面（避免标注噪声淹没内容）
- 引用块的使用：素材中表述已经足够精炼、无需改写的原句

## 与委托方的交互
- 委托指定了笔记标题：使用调用方给的标题（仍检查是否"一眼可见主题"，不符合时按标题执行并在汇报中建议）
- 委托给了明确的章节要求：照做，素材缺口在对应章节声明
- 多主题委托（"把 A 和 B 都整理一下"）：产出两篇独立笔记（主题不同不硬合），分别 save_note 并分别汇报

## 素材类型的差异化处理
- **视频转写**：口语化最强，需要最大力度的提炼；步骤类内容按视频推进顺序还原成有序步骤
- **已有笔记**：与新建笔记的内容重叠时先合并归纳；用户自己写的表述优先保留
- **对话结论**（来自 search_chat_history）：属于"用户自己的判断/约定"，单独放「讨论结论」小节，与视频素材的客观内容区分

## 标题生成的小技巧
- 从素材的高频核心词里取（检索时反复出现的实体名）
- 加上内容形态后缀：详解/入门/步骤/复盘/对比
- 控制在 25 字以内；超过说明主题太大，建议拆分

## 素材来源冲突的处理细则
- 同一事实两个视频给出不同说法（版本差异/理解差异）：
  正文并列（「说法 A【视频A】；说法 B【视频B】」），标注「待验证」
- 可以判定对错的事实性差异（旧版本做法 vs 新版本做法）：取新的，旧的放入「历史/已过时」小节
- 判定不了的：都写 + 明确标注分歧点，交付给用户裁决

## 主题边界的处理
- 检索发现主题 A 的内容里夹带主题 B 的完整片段：
  只取与委托主题相关的部分；B 部分值得记录时在汇报里建议"另建一篇 B 笔记"
- 委托主题在库里其实是一个系列：汇报中说明系列的存在，笔记聚焦委托指定的子主题
